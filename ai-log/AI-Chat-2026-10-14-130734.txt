  3. Data model

  type Park = {
    id: string;
    name: string;
    description?: string;
    address?: string;
    coords?: { lat: number; lng: number };   // present only if both finite and 
  in range
    amenities: string[];                     // [] if absent; slugs kept raw
    hours?: string;
    images: string[];                        // only non-empty http(s) strings
    acreage?: number;                        // finite and >= 0
    rating?: number;                         // finite
  };
  - normalizePark(raw: unknown): Park | null is the only place raw JSON is
    touched.
  - loadParks(raw: unknown): { parks: Park[]; skipped: number }. Duplicate ids:
    keep the first and count the rest as skipped.
  - Trimmed strings; empty or whitespace becomes absent.
  - images accepts only http:/https: URLs, which blocks javascript: and data:
    values from the dataset.
  - Out-of-range lat (±90) or lng (±180) means no coords.
  - I'm treating acreage: 0 and rating: 0 as real values, not missing. Flagging
    that choice for review.

  5. Accessibility strategy

  - Semantics: one <h1> ("Find a Park"). Landmarks: header, nav/list region,
    main for details, and a labelled map region. The list is a real <ul> of real
    <a href="#/parks/…"> links, with aria-current="page" on the selected one.
  - Focus:
    - Opening details moves focus to the details <h2 tabIndex={-1}>.
    - Back moves focus to the list link that opened it. If the park isn't in the
      list (a direct URL), focus goes to the list heading.
    - A marker click behaves like a list click.
    - Focus is moved only on user-initiated selection, not on first page load.
  - Live region: one polite role="status". It announces "Showing details for
    {name}" and "Showing all {n} parks". Result counts come with filters, if
    added.
  - Map as enhancement: keyboard-focusable markers with alt/title set to the
    park name, plus a short note ("The list has the same parks"). No information
    appears only on the map. Tile failure leaves the list and details
    unaffected.
  - Visual: :focus-visible outline with ≥3:1 contrast, targets ≥24×24, reflow at
    320px, prefers-reduced-motion honored (no animated pan or zoom).
    Text/background pairs are checked with a contrast tool, not eyeballed.
  - Document: document.title updates with the selected park.

  6. Security specifics (SECURITY.md)

  - Text rendered via JSX only. No dangerouslySetInnerHTML.
  - External links use rel="noopener noreferrer".
  - Marker names go through Leaflet's title/alt options, not HTML popups.
  - Leaflet's default marker icons are bundled from the package. No CDN.
  - CSP (stage 5): tiles from tile.openstreetmap.org. img-src must allow any
    https: because the real image hosts are unknown, which I'll call out as

  How it behaves

  - The list is a <ul> of real <a href="#/parks/<id>"> links. The selected one
    has aria-current="page".
  - Focus: after a hash change, focus goes to the details <h2>. On back it
    returns to the originating link, or to the list heading if that link isn't
    found. On first load focus is not moved.
  - Live region: role="status" announces "Showing details for X", "Showing all N
    parks", or "Park not found". It is empty on load.
  - Missing data: rows and sections render only when the value exists. A park
    with no coordinates gets "Not shown on the map."
  - Unknown id: shows a "Park not found" heading and a back link.
  - Phone (<700px): CSS shows the list when nothing is selected and the details
    when something is. Desktop shows both in two columns.

  Review focus (1-3)

  1. The two focus effects in App.tsx (lines ~25-48). The logic depends on
     effect declaration order: the focus effect must run before the effect that
     updates previousIdRef.
     - How it could be wrong: a reordering silently breaks focus return. The
       effect also fires on every selectedId change, so a future "select via
       map" must go through the hash or focus handling will diverge. React
       StrictMode double-runs effects in dev, but the navigations === 0 guard
       should prevent a focus steal. I did not test dev-mode StrictMode
       specifically.
  2. useHashRoute + parseHash. Everything depends on it.
     - How it could be wrong: if the hash changes between the initial useState
       read and the effect subscribing, one change is missed. That window is
       tiny but real. Also, the navigations counter is only incremented on
       hashchange, so programmatic history.pushState calls would not move focus.
  3. ParkDetails.tsx conditional rendering. This is where "never invent data" is
     enforced.
     - How it could be wrong: String(park.acreage) and String(park.rating)
       display raw numbers (4.7, 526) with no units or scale, which is
       deliberate under D9 but reads sparse. Zero values do render ("Rating 0"),
       which is intentional but could look odd.

  Uncertainties and trade-offs

  - Heading focus ring. I suppress the plain :focus outline on h2 and show it
    only on :focus-visible. Browsers may not show :focus-visible for
    script-focused headings after a mouse click, which is acceptable since
    headings aren't controls, but the keyboard case should be checked by eye.
  - "Not shown on the map" renders now even though there is no map until
    stage 3. Right now every park without coordinates (none in the sample) would
    show it.
  - Static copy (header subtitle "NYC sample parks", "Select a park…", "Image
    unavailable") is UI text, not park data.
  - Phone layout hides the list with display: none, which also removes it from
    the accessibility tree. That's intended while details are shown, but it
    makes the browser's back button essential. The in-page "All parks" link
    covers it.
  - No test for layout or CSS at all.

  Real finding worth knowing

  From reading Leaflet's source: markers get role="button" and tabindex="0", but
  Leaflet only turns Enter into a click when a marker has a popup. As shipped,
  a marker would be focusable and do nothing on Enter. I handle keydown (Enter
  and Space) explicitly and tested it. A Playwright keyboard test in stage 4
  should confirm it in a real browser.

  Behavior

  - Marker click, Enter and Space call onSelect, which sets location.hash. From
    there the same code as the list runs (focus to heading, announcement,
    title).
  - The selected marker is larger and recoloured via a CSS filter, so it isn't
    colour-only.
  - It pans to the selected marker only if it's outside the view, and it
    respects prefers-reduced-motion.
  - Parks without coordinates are not on the map. If none have coordinates, the
    map is replaced by a message.
  - If the map throws, the MapBoundary message appears and the list/details keep
    working (tested with a throwing mock).
  - DOM order is list, details, map, which matches the visual order at every
    width.

  Review focus (1-3)

  1. ParkMap.tsx effects 2 and 3 (marker creation and selection sync).
     - How it could be wrong: effect 3 is declared after effect 2 and relies on
       markersRef already being filled. A reorder breaks selection styling
       silently. Effect 2 recreates every marker when parks or onSelect changes.
       selectPark is module-level for that reason, but an inline callback would
       rebuild markers on every render and drop focus.
  2. Leaflet's DOM from the outside. marker.options.icon !== icon pokes at
     Leaflet internals, and setIcon recreates the icon element, so a focused
     marker loses focus when selection changes. The app moves focus to the
     details heading anyway, but a future "keep focus on the marker" feature
     would hit this.
  3. MapBoundary + effect errors. I'm relying on React's behavior that errors
     thrown in effects reach the nearest error boundary. The test throws during
     render, not inside an effect, so the effect-error path is not directly
     tested.
